# Secure operation

Passwords are stored as randomly salted scrypt hashes (N=131072, r=8, p=1). A legacy bcrypt hash is upgraded after a successful sign-in. Changing a password or username invalidates that user's existing sessions. Rotating `APP_SECRET_KEY` invalidates all sessions.

Staff accounts have administrator, manager, or editor roles. Authorization is enforced server-side on every protected route, not by hidden navigation alone. Administrators manage critical settings and accounts; managers can request an editor's deletion, which remains pending until an administrator approves it. Account removal and demotion cannot leave the site without an active administrator. Sensitive account changes require current-password verification.

Editor workspace access is restricted to downloads, categories, tags, and media owned by that user's immutable account ID. Unattributed legacy records remain staff-only. Lists, relationship loads, aggregate counts, direct IDs, bulk writes, file routes, media transformations, and upload-progress tokens enforce this boundary. Editors cannot attach another owner's taxonomy, parent content, or local media, or mutate owned taxonomy/media used by another owner. Published content remains publicly readable; workspace isolation is not an access restriction on the public catalog.

Removing editor content hides it from visitors and creates a pending staff-reviewed deletion. The editor can withdraw the request; administrators and managers can reject it or approve permanent deletion. Review and withdrawal are serialized with session/role revalidation under a SQLite write lock. Category, tag, and media removal do not use this content-specific review workflow.

The protected default category is the single shared exception to editor ownership: editors may assign content to it but cannot modify, move out of, reorder, or delete it. Administrators and managers configure its name and description. Category moves transfer all matching records, including drafts and trash, rather than copying them; an editor cannot move content owned by another user.

Unverified editor submissions and changes to published content require staff publication approval. Bulk publishing and public version-history changes follow the same policy. Unverified editors cannot replace media used by a live publication in place; they must upload a new asset and submit the content change for review. Verification changes require the acting administrator/manager's current password and account revalidation under the database write lock. Editor content writes refresh verification and credential/session validity under that lock. Review actions require the exact content revision shown to the reviewer. Verification revocation affects future changes, not existing publications; granting verification does not implicitly approve pending submissions.

Editor correspondence is private to its sender and administrators/managers. Messages and replies are bounded plain text, escaped on render, protected by CSRF, and restricted to five submissions per editor per hour. Message bodies, replies, and review feedback are not copied into audit records. This is access-controlled server-side storage, not end-to-end encrypted messaging.

First-run setup requires a private `SETUP_TOKEN` to verify server ownership. The token is not written to URLs, cookies, or audit logs. Generate or rotate it with `make setup-key`, then restart the server. Public content, administration, and uploads stay closed until installation finishes. Migrations preserve the installed status of existing sites.

Maintenance actions require the current password, a session-bound confirmation valid for five minutes, and an exact match of the site name. Every scope invalidates old administrator sessions, including on public pages. SQLite-backed attempt limits protect setup, sign-in, password verification, and reset actions. Sensitive forms have a 16 KiB request-body limit, including streamed requests without a content-length header.

An operating-system lock enforces a single application process. A reset waits for active requests and background work. If cleanup is interrupted, a persistent maintenance marker keeps the site closed until cleanup resumes at startup. Deletion is limited to two validated data roots; broad, overlapping, code, database, or symlink roots are rejected. Targets outside those roots are not followed.

SQLite `secure_delete` is enabled, but SSD behavior, WAL files, operating-system snapshots, and external backups prevent a guarantee of forensic erasure. A full reset does not remove `.env` secrets, the hosting account, or external backups. Returning to setup does not remove the application code.

In production, set `APP_BASE_URL=https://your-domain` and terminate HTTPS at a trusted reverse proxy. This enables Secure cookies and HSTS. Trust forwarded headers only from the real proxy addresses; do not use an unrestricted `forwarded-allow-ips`.

Keep `.env` and the SQLite database outside the web root and accessible only to the service account. Never commit `.env`. Rotate previously disclosed keys; removing a key from Git history alone is insufficient.

The application does not encrypt its entire SQLite database. Use operating-system disk encryption and encrypted backups where needed. Password hashing and data encryption address different risks. Published downloads remain readable by visitors.

The database does not store raw client IP addresses or browser user-agent strings. Quotas use keyed HMAC client identifiers; rotating `APP_SECRET_KEY` also resets their continuity. Existing stored addresses are anonymized by the user-account migration, historical audit entries containing addresses are redacted, and the legacy administrator credential copy is removed after transfer to the users table. Default Uvicorn access logging is disabled in the supplied Makefile. Check reverse-proxy, hosting, backup, and operating-system logs separately; the application cannot control those external records. Public HTTP errors are recorded as `anonymous` with route patterns rather than full URLs or request bodies. Failed sign-ins and rate-limit events are marked critical. Audit records are subject to the configured retention limit of 50, 100, 200, 500, or 800 records; they are not an immutable external security archive.

Passwords are not end-to-end encrypted: this server must verify them. They are protected in transit by HTTPS and stored as one-way salted hashes. Published site content and server-managed private pages are likewise not end-to-end encrypted. Use encrypted backups and disk encryption when protecting data at rest.

The supplied server commands use `app/logging.json` for English, plain-text UTC console logs. Terminal controls are escaped. Exception traces include error types and code locations, but omit exception values and source lines because those may contain submitted secrets or SQL parameters. Account mutations revalidate the acting session and role after acquiring the database write lock.

Stop the server with `Ctrl+C` in the terminal running `make dev`. Restart after changing `.env`.

## Encrypted backups and restore

Only administrators can configure, create, download, import, or delete backups. Mutations require CSRF protection, a rate-limited current-password check, and fresh role/session verification under the SQLite write lock. The latest encrypted backup cannot be deleted; a successful new backup retains the latest plus at most seven historical archives (eight total). Failed backups do not prune history.

The browser generates an RSA-OAEP 4096-bit key pair. Only the public key is saved on the server. The private PKCS#8 key is exported in a recovery file encrypted with AES-256-GCM and a PBKDF2-SHA256 password-derived key (600,000 iterations, random salt). Keep the recovery file and its password offline: neither is uploaded, and there is no recovery backdoor. Archives use a fresh AES-256-GCM key and nonce, with the content key wrapped using RSA-OAEP-SHA256 and authenticated envelope metadata. Backups protect exported copies, not the original running site's unencrypted database or a compromised server.

Use HTTPS (localhost is permitted for development). Import decryption happens in the browser; large archives require sufficient browser memory. The plaintext import is uploaded over the same-origin HTTPS connection to private storage for a 15-minute review window. Strict archive paths, size limits, schema/type checks, signed administrator-bound review tokens, password re-verification, exact current-site-name confirmation, and an irreversible-action checkbox precede restoration. A protective encrypted backup is required before replacement. The current administrator credentials and backup public key are preserved; session generation is rotated. Database restoration is transactional and media swaps use a crash-recovery journal. Abandoned imports are cleaned periodically while the application runs.

Archives contain application database records and both upload directories; they exclude application code, `.env`, runtime secret keys, Alembic files, and backup history. Restore requires the exact application schema and media/backup roots on the same filesystem. Automatic backups run only while the single-worker application is running; overdue intervals are caught up on startup. Snapshot/restore operations briefly serialize site requests for consistency. No automatic backup is enabled until an administrator configures it.

Trash retention is opt-in and admin-controlled: 15, 30, 60, 90, 120, 240, or 360 days. Existing ordinary trash is covered when enabled. Pending editorial deletion requests and their version families are excluded. Retention deletes content records, not independently managed media-library assets. Hidden downloads are excluded from public lists, search, sitemap, version relationships, and direct download routes; hiding is not encryption or deletion of uploaded files.
